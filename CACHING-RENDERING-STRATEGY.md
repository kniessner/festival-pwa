# Festival PWA — Caching & Rendering Improvement Strategy

**Date:** 2026-07-11  
**Context:** The production Festival PWA plugin suffers from a broken/offline-looking UI, missing or partial content, and inconsistent styling. Investigation shows that the root causes are a combination of **weak/naïve Service Worker caching**, **fragile HTML extraction/snapshotting**, and **chaotic DOM rendering** of scraped content.

This document synthesizes best practices from the referenced PWA guides and builds a concrete solution plan for the codebase.

---

## 1. Root-Cause Diagnosis

### 1.1 Caching problems

| Symptom | Why it happens | Evidence in repo |
|---------|---------------|------------------|
| Offline mode shows stale or no content | The production SW (`pwa/sw.js`) caches the dynamic manifest **once at install**. If the admin syncs new content, the SW is never updated and still serves the old cache. | `pwa/sw.js` uses a static `CACHE_NAME = 'bucht-v3-fragment'`. No versioning or update check. |
| First offline launch fails | The dynamic precache in `pwa/sw.js` relies on fetching `/pwa/data/_manifest.json` and every page JSON during install. If the network is flaky or one fetch fails, the promise chain logs but still resolves, leaving partial data. | `precacheDynamic()` catches per-page errors but adds all-or-nothing via `cache.addAll()`. |
| Cross-origin assets (images, fonts, CSS from source site) break offline | Snapshot mode caches source-site assets with `mode: 'no-cors'`, producing **opaque responses** that may not render or may become invalid. | `pwa/sw.js` lines 68–74: `fetch(url, { mode: 'no-cors' })` + `cache.put`. |
| Standalone SW can serve stale assets forever | `standalone/sw.js` uses a hardcoded cache name that is never bumped, and there is no update flow. | `standalone/sw.js` line 1: `CACHE_NAME = 'bucht-standalone-v1783732870'`. |
| Cache name collision | Both production and standalone can share origin/scoped caches. | Production and standalone both run under the same origin when embedded in WP. |

### 1.2 Content / extraction problems

| Symptom | Why it happens | Evidence in repo |
|---------|---------------|------------------|
| FAQ answers are empty | `extract_faq()` expects accordion markup or sibling paragraphs. If the source site uses JS-driven accordions, lazy-loaded content, or blocks, extraction misses the answers. | `pwa/data/cashless.json` and `preview/data/cashless.json` have 16 questions, all answers `""`. |
| Production manifest has only 1 page | `_manifest.json` is written only from successfully synced slugs. Failed/incomplete syncs leave a tiny manifest. | `pwa/data/_manifest.json` currently only lists `cashless`. |
| Corrupt `.json` file | A page without a slug was saved as `.json`. | `pwa/data/.json` exists with empty slug/title/content. |
| Snapshot pages look broken | Snapshot CSS tries to hide site chrome with broad selectors, but modern block themes inject layout CSS that still leaks in. Shadow DOM isolation in the app helps, but the snapshot fragment is dumped as raw HTML with inline styles that may reference missing assets. | `class-content-sync.php` `extract_snapshot()` injects isolation CSS and rewrites URLs, but asset caps and cross-origin opaque caching make it fragile. |
| Raw pages lose original design | `renderRaw()` injects saved external stylesheets into a shadow root. Many source stylesheets contain relative URLs or depend on body/html classes that do not exist inside the shadow tree. | `pwa/js/app.js` `renderRaw()` lines 220–263. |

### 1.3 Rendering / DOM problems

| Symptom | Why it happens | Evidence in repo |
|---------|---------------|------------------|
| Chaotic DOM | `index.html` mixes inline `<style>`, inline `<video>` placeholder, and DOM that should be generated by JS. | `standalone/index.html` contains a full `<video>` block and a leftover heading. |
| Missing bottom nav / blank content | `standalone/js/router.js` uses `innerHTML` to swap whole pages. Any JS error during render leaves a blank `content` div. | No error boundary in `loadPage()`. |
| Content flashes or reloads on every nav | Raw/snapshot fragments are fetched **every time** the user opens the page, even when already cached. | `renderSnapshot()` always calls `fetch(fragmentUrl)`. |
| Search breaks after navigation | `setupSearch()` is bound to a specific `#searchInput` node that is destroyed and recreated by `innerHTML` navigation. | `standalone/js/app.js` comment explicitly documents this workaround. |
| HTML/inline styles leak into app shell | `renderRaw()` and `renderSnapshot()` inject external CSS that can override app shell styles. Shadow DOM mostly contains it, but the host page can still be affected by global selectors in inlined stylesheets. | Snapshot isolation CSS uses `!important` broad selectors but cannot catch every theme class. |

## 2. Best Practices from the Articles (Synthesized)

The six articles agree on a small set of non-negotiable rules for reliable offline PWAs:

1. **Version the cache per deployment.** Change the cache name whenever the app shell, data, or assets change. Old caches are deleted in `activate`.
2. **Use strategy per resource class**, not one strategy for everything. Specifically:
   - App shell / static assets → **Cache-First**.
   - HTML pages / app content → **Network-First** with cache fallback.
   - API JSON → **Stale-While-Revalidate** (fast from cache, refresh in background) or **Network-First**.
3. **Avoid `cache.addAll()` for long or optional lists.** Use per-asset `cache.put()` wrapped in `Promise.allSettled()` so one failure does not abort the whole install.
4. **Bypass the browser HTTP cache during SW install/update.** Use `cache: 'no-cache'` (or rely on versioned URLs) so the SW fetches fresh assets.
5. **Handle opaque cross-origin responses carefully.** Prefer CORS-enabled assets or proxy them same-origin. Opaque responses occupy quota and cannot be inspected.
6. **Keep `skipWaiting()` controlled.** Use it, but notify the page about updates and let the user reload, or auto-reload once when safe.
7. **Use IndexedDB for structured app data, not just Cache API.** Cache API is for HTTP responses; IndexedDB is for parseable content, user data, and offline queues.
8. **Guard fetch with timeouts and retry logic**, and handle `QuotaExceededError` per file.
9. **Test offline with DevTools, not just by toggling Wi-Fi.** Use Application → Cache Storage, Service Workers, and Lighthouse.
10. **Simplify rendering architecture.** A chaotic DOM is harder to cache and harder to render consistently. Prefer a clean app shell + data-driven templates over injecting raw scraped HTML.

## 3. Strategic Solution Plan

### 3.1 Immediate wins (this week)

#### A. Fix the Service Worker versioning/update model
- Introduce a build/version stamp (`FESTIVAL_PWA_VERSION` or a generated hash) that is injected into both `pwa/sw.js` and `standalone/sw.js`.
- Change the cache name to include the version, e.g. `bucht-pwa-v${VERSION}`.
- In `activate`, delete every cache whose name does not match the current version.
- Add a message channel from SW to page: when a new SW installs, notify the page and offer a non-intrusive "Update available — reload" banner.
- For standalone, keep the version in `standalone.json` and bump it on every data update.

#### B. Harden precaching
- Stop using `cache.addAll()` for the dynamic page list. Precache the shell atomically, then precache data files one-by-one with `Promise.allSettled()` so a missing/failed page does not abort the install.
- Add `cache: 'no-cache'` to install-time fetches so the browser does not return a stale HTTP-cached manifest/data file.
- Add a per-fetch timeout using `AbortSignal.timeout()`.
- Remove `mode: 'no-cors'` cross-origin asset caching in production. Instead:
  - Snapshot assets are downloaded server-side by the PHP syncer and served from `/pwa/cache/` (same-origin). The SW should cache them normally.
  - Remote fonts (Google Fonts) should either be self-hosted or fetched with proper CORS. If CORS is unavailable, accept that they may be missing offline rather than storing opaque garbage.

#### C. Stop rendering raw snapshots in shadow DOM
- Replace `renderSnapshot()` and `renderRaw()` with a **structured-content renderer**.
- Keep `snapshot` mode only as a fallback for pages that cannot be structured, and render them in an **isolated `<iframe>`** with a `sandbox` attribute instead of shadow DOM. This gives a real document context for the source CSS without leaking styles into the app.
- For FAQ / Grid / Generic types, render with the existing app CSS and the extracted JSON data. This is the only way to guarantee a consistent, offline-capable, DOM-clean result.

#### D. Clean up the app shell DOM
- Remove the inline `<video>` block and stray heading from `standalone/index.html`.
- Make `pwa/index.html` and `standalone/index.html` identical except for relative paths. Extract shared CSS into `css/tokens.css`, `css/base.css`, etc.
- Add a small error boundary in `loadPage()` / `renderContent()` so a render failure shows a friendly message instead of a blank screen.

### 3.2 Short-term improvements (next 2 weeks)

#### E. Rebuild the extraction engine for reliability
- Replace the heuristic DOM scraping with **selector-based extraction** configured in the admin per page:
  - FAQ: selector for question node + answer node (e.g. `.faq-question`, `.faq-answer`) and optional expand/collapse.
  - Grid: selector for card + title + description + image.
  - Generic: selector for main content.
  - Snapshot: only for pages that truly need the original markup.
- Add a **live preview** in the admin: show extracted JSON for one page before syncing all pages.
- Add a fallback: if extraction yields empty content, keep the previous version and flag the page as stale instead of writing empty JSON.

#### F. Improve content freshness
- Add a `synced_at` timestamp and an `etag`/`hash` per page JSON.
- On app launch, fetch `_manifest.json` with `cache: 'no-cache'`. If `synced_at` is newer than the cached copy, refresh data in the background.
- Use **Stale-While-Revalidate** for all `/wp-json/festival/v1/*` endpoints.

#### G. Use IndexedDB for offline data resilience
- Move page data from the Cache API to IndexedDB (or idb-keyval) on first successful fetch.
- The app shell loads from cache, then reads JSON from IndexedDB. This decouples data from HTTP response caching and makes offline navigation reliable even when individual cache entries are evicted.
- Store user favorites, dismissed announcements, and last-viewed page in IndexedDB (standalone currently uses `localStorage`; that is acceptable but IndexedDB is more robust for larger data).

#### H. Add a real offline indicator and error messages
- Keep the offline badge.
- Add a "Last updated: …" line using `_manifest.json.synced_at`.
- When a page is missing offline, show: "This page is not available offline yet. Connect to the internet and open it once to cache it."

### 3.3 Medium-term architecture changes (next month)

#### I. Unify production and standalone frontends
- Merge `pwa/js/app.js` and `standalone/js/app.js` into one module that detects whether it is running inside WordPress (REST API available) or standalone (static JSON files).
- Share all view/render modules between both builds.
- Use the same CSS files for both.

#### J. Replace the WP Cron async sync with a robust queue
- Current async sync processes one page per cron event. If cron is unreliable, the sync never finishes.
- Add an admin "Sync now" button that triggers a server-side loop with `set_time_limit(300)` and optional background processing via Action Scheduler or WP CLI.
- Save per-page status so the admin can see which pages failed and why.

#### K. Add a Service Worker update check for long-lived installed apps
- Use `registration.update()` on page load, or a periodic `setInterval` inside the SW (where supported) to detect new versions.
- Notify the user with a non-intrusive banner.

#### L. Audit and cap cache size
- Track the size of cached assets. If quota is exceeded, evict large opaque responses first, then old snapshots.
- Prefer same-origin assets; avoid caching large source videos or full-size galleries.

## 5. Implementation Order Recommendation

1. **Data quality first** (tasks 7, 8): without correct content, better caching is meaningless.
2. **Shell + SW reliability** (tasks 1–5): fix the broken offline experience and chaotic DOM.
3. **Rendering architecture** (tasks 6, 12): make pages render consistently and beautifully.
4. **Advanced caching + IndexedDB** (tasks 9, 10, 13, 14): make the PWA fast and production-grade.

## 7. Anti-Patterns to Stop

| Stop doing | Why | Replacement |
|------------|-----|-------------|
| `mode: 'no-cors'` for cross-origin assets | Creates opaque responses that may not render and waste quota. | Serve assets same-origin via PHP sync, or use CORS-enabled assets. |
| `cache.addAll()` for dynamic page list | One failed fetch aborts the whole precache. | Per-asset `cache.put()` with `Promise.allSettled()`. |
| Static `CACHE_NAME` across deployments | Users never get fresh content without manually clearing cache. | Versioned cache name + update banner. |
| Injecting raw scraped HTML into shadow DOM | CSS/JS context is wrong; styles leak; DOM is unpredictable. | Structured JSON renderers or sandboxed iframe. |
| Relying only on Cache API for data | Cache entries can be evicted silently; responses are hard to query. | IndexedDB for structured data + Cache API for HTTP responses. |
| Ignoring failed sync pages | Leaves empty/corrupt JSON and tiny manifests. | Per-page status, fallback to previous version, admin reporting. |
